# Implementation Plan

## Purpose

Build a typed research framework for regime-switching analysis that can compare statistical regime models, change-point detectors, clustering baselines, and supervised or pseudo-supervised classifiers under reproducible, live-equivalent validation rules.

## Architectural decisions

1. **Use a src-layout Python package.** Core workflow code belongs under `src/regime`, split by data ingestion, features, models, validation, evaluation, backtesting, reporting, experiments, and synthetic data.
2. **Keep research outputs separate from source code.** Generated reports, experiment artifacts, notebooks, and local caches should not become import-time dependencies.
3. **Represent all regime outputs as dated probability tables plus metadata.** A hard label is always derived from an explicit probability source and decision rule.
4. **Treat filtered and smoothed probabilities as different products.** Filtered probabilities use observations through time `t` and are eligible for live-equivalent decisions. Smoothed probabilities use future observations after `t` and are restricted to hindsight diagnostics, visualization, and pseudo-label generation.
5. **Treat change points and recurring latent states as distinct target concepts.** Change-point methods identify event boundaries or segment breaks. Regime-switching and clustering methods infer recurring states that may appear, disappear, and reappear.
6. **Separate statistical fit from economic usefulness.** Likelihood, AIC, BIC, calibration, and classification metrics are necessary diagnostics, but deployment candidates must also pass out-of-sample economic tests after realistic costs and constraints.
7. **Separate supervised labels from pseudo-label replication.** Supervised labels are externally defined business or empirical targets. Pseudo-labels are generated by another model, such as smoothed HMM states, and can only validate replication fidelity unless independently tested economically.
8. **Separate live-equivalent information sets from hindsight diagnostics.** Model selection and deployment claims must be based on information available at the decision timestamp. Hindsight analyses can explain behavior but must be tagged as non-live.

## Implementation phases

### Phase 0: Repository foundation

- Define package metadata, optional dependency groups, formatting, linting, typing, and test timeout policy.
- Establish importable top-level packages for every planned workflow area.
- Add root planning documents describing architecture, schemas, evaluation rules, risks, and acceptance criteria.

### Phase 1: Data contracts and ingestion

- Implement typed data schemas for prices, returns, macro series, features, labels, probabilities, positions, trades, and metrics.
- Add adapters for local Parquet, CSV, and DuckDB sources.
- Implement calendar alignment, missing-data policies, point-in-time timestamp fields, and leakage checks.
- Acceptance criteria:
  - Every dataset has a schema version.
  - Every feature row has `as_of_ts` and `available_ts`.
  - Validation fails on duplicate entity-time keys or future availability timestamps.

### Phase 2: Feature and target engineering

- Implement return, volatility, drawdown, liquidity, spread, trend, macro surprise, and cross-sectional features.
- Implement label builders for supervised labels and pseudo-label builders for replication tasks.
- Add deterministic train/validation/test split generation with purging and embargo.
- Acceptance criteria:
  - Feature functions are pure and deterministic.
  - Labels record their source type: `supervised`, `pseudo_filtered`, `pseudo_smoothed`, or `diagnostic`.
  - Split manifests are saved with exact dates and embargo settings.

### Phase 3: Baseline models

- Implement statistical baselines: Gaussian mixture, Markov switching, HMM, rolling volatility threshold, and change-point detectors.
- Implement machine-learning baselines: logistic regression, random forest, gradient boosting, SVM, and optional neural sequence models.
- Standardize model outputs to probability tables and run metadata.
- Acceptance criteria:
  - Every model exposes fit, predict, score, and serialize interfaces.
  - Probability outputs declare whether they are filtered, smoothed, static, or retrospective.
  - Change-point outputs declare boundary timestamps and segment IDs separately from recurring state IDs.

### Phase 4: Validation and evaluation

- Add walk-forward, expanding-window, rolling-window, purged k-fold, and fixed holdout validators.
- Add statistical diagnostics, replication metrics, economic metrics, and sensitivity analyses.
- Add report templates that display live-equivalent and hindsight results in separate sections.
- Acceptance criteria:
  - Evaluation rejects smoothed probabilities in live-equivalent backtests unless explicitly marked as a hindsight diagnostic.
  - Reports show statistical fit and economic usefulness as separate scorecards.
  - All tests run with explicit timeouts.

### Phase 5: Backtesting and decision policies

- Implement probability-to-position policies, transaction-cost models, turnover controls, and risk overlays.
- Add delayed execution, slippage assumptions, and rebalancing calendars.
- Acceptance criteria:
  - Backtests consume only filtered or otherwise live-eligible signals.
  - Position decisions record signal timestamp, execution timestamp, and data availability timestamp.
  - Results include net-of-cost Sharpe, drawdown, turnover, hit rate, exposure, and capacity diagnostics.

### Phase 6: Experiment management and reporting

- Add experiment manifests, reproducible config snapshots, random seed tracking, model cards, and dataset cards.
- Generate Markdown and HTML reports for model comparison.
- Acceptance criteria:
  - Every run can be reproduced from a saved manifest.
  - Model cards identify intended use, non-use cases, leakage controls, and known risks.
  - Quick-start tasks remain ordered from environment setup through final report generation.
